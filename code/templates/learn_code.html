In short

If you read one screen, read this one.

This is a Flask app. It has routes, a template, some vanilla JS, and a WebSocket. If you have shipped a web app, you already know eighty percent of the file listing.

The other twenty percent is where all the difficulty lives, and it comes from two facts that no web app has to deal with: the data never stops arriving, and there is exactly one radio. Almost every design decision below — the arbiter, the real OS threads, the emit bridge, the queue-of-one — is downstream of one of those two.

What it does

Tunes an RTL-SDR, demodulates audio, cuts it into transmissions, transcribes them on an NPU, and pushes the text to a browser — while nine other decoders queue up for the same antenna.

Shape of it
  • 13,700 lines of Python across 41 modules
  • 5,300 lines of vanilla JS, no build step
  • 33 test files, none needing a radio
  • One process owns the hardware
The one thing to take away

A web request is a transaction: it arrives, you serve it, it is over, and if you block for 300 ms a user waits 300 ms. Here, blocking for 300 ms means 300 ms of radio you will never get back, and blocking forever — which is the default behaviour of reading a pipe — silently freezes the entire server. Section 3 is that bug, three times, in three different disguises.

1 Two facts that shape everything

Why this isn't just a CRUD app with an antenna.

Fact one: the data never stops

A web server is idle by default. It sits in an accept loop burning nothing until someone shows up. Work is pulled in by requests, and if nobody requests anything, nothing happens and that is correct.

A radio is the opposite. The dongle produces 2.4 million samples per second whether or not anyone is listening, and it does not buffer politely — if you are not there to read it, the samples are gone. Work is pushed at you, forever, and "keeping up" is the entire job.

You already know this

A WebSocket firehose you cannot unsubscribe from, or a Kafka consumer where falling behind means dropped records rather than a growing lag metric. Backpressure is not an option because the producer is physics.

→
Here it is in this repo

Every stage is a queue with a bounded size and an explicit policy for what to throw away when it fills. maxsize=200 on both audio paths, input_source.py:52.

That produces a design rule you will see repeatedly: decide, at every queue, who is allowed to be dropped. The two audio queues answer it differently, and the asymmetry is deliberate (tuner.py:403-420):

self.pcm_queue.put(chunk, timeout=0.5)   # to the transcriber — waits up to 500ms
self.audio_queue.put_nowait(chunk)       # to the browser — drops instantly if full

A browser that stalls must never be able to slow down transcription. The recording is the product; the live listen is a convenience. One line of code, and it encodes a product decision.

Fact two: there is exactly one radio

Nine decoders want the dongle. Only one can have it, because each of them opens the USB device directly — rtl_433, dump1090, acarsdec and friends are separate C programs that know nothing about each other. Two at once produces usb_claim_interface error -6 and both lose.

You already know this

A connection pool of size one. Or a feature that must run on exactly one node, so you reach for a distributed lock and spend a week on the edge cases around who holds it and what happens when they die.

→
Here it is in this repo

sdr_arbiter.py — and notably not a lock. It is a queue of depth one with a single worker, for reasons that took a while to learn. Section 4.

The bit that surprises web people. Switching frequency is not a function call, it is a process lifecycle: kill rtl_fm, wait for the kernel to release the USB claim, spawn a new one, wait for it to open the device. That takes one to two seconds. HTTP requests arrive in milliseconds. Everything about the arbiter follows from that ratio.

3 The event loop, and three ways I froze it

The one concept that transfers directly from Node — and the one place it bites harder here.

The very first two lines of app.py, before any other import:

import eventlet
eventlet.monkey_patch()

eventlet is Node's event loop, retrofitted onto Python. monkey_patch() reaches into the standard library and replaces threading, socket, time and subprocess with cooperative green versions. After that line, time.sleep(1) does not sleep a thread — it yields to the hub, exactly like await setTimeout. Thousands of concurrent connections, one OS thread, no locks needed.

And the same catch as Node: one greenthread that blocks without yielding freezes everything. Every HTTP request, every WebSocket, every timer. If you have ever locked up a Node server with a synchronous readFileSync in a hot path, you know this failure exactly.

What makes it worse here is what we block on. A web app blocks on files and sockets, which eventlet patched, so they yield and you never notice. This app blocks on pipes from child processes — and a pipe read is the one thing that is genuinely, unavoidably blocking. Three times, in three disguises:

Disguise one: the reader that never returns

1
The meteor detector spawns rtl_fm and reads its output in a loop: raw = self._process.stdout.read(chunk_bytes).
2
On a quiet frequency, rtl_fm produces nothing. The read blocks. Under a green thread, blocking means the hub never runs again.
3
Symptom: the whole web console hangs. Not slow — hung. CPU at 1.2%, so it doesn't even look like a spin; it looks like a dead process that is somehow still alive.
4
Fix: make that one thread a real OS thread, so its blocking is its own problem.
# meteor_detector.py:12-22
# Use REAL stdlib modules, not eventlet's green versions. The monitor thread does
# a blocking read on rtl_fm's stdout pipe; under a GREEN thread that blocking read
# stalls the entire eventlet hub (all HTTP/Socket.IO freezes), so the reader must
# be a real OS thread.
try:
    from eventlet.patcher import original
    subprocess = original("subprocess")
    threading = original("threading")
except ImportError:
    import subprocess
    import threading

eventlet.patcher.original() hands back the unpatched module. It is the escape hatch: "this part is not cooperative, give me a genuine thread." Eleven modules use it, each one guarding a blocking read.

Disguise two: closing the pipe deadlocks too

Having made the reader real, changing frequency still hung — but only sometimes, and only after presets gained squelch. The reader thread sits inside stdout.read(4096), which holds the BufferedReader's internal lock. The tuner then calls close() on that same pipe. close() wants the lock. Nobody moves.

The order matters, and tuner.py:358-372 spells it out: kill the process first, then close the pipes. Killing makes the read return empty, which releases the lock, which lets the close succeed.

Why squelch exposed it. With squelch at 0, rtl_fm emits constant FM hiss, so read() always had bytes and always returned promptly. The deadlock existed the whole time and was masked by noise. Turning on squelch — a feature — produced silence, and silence produced a hang. The bug was in the shutdown path; the trigger was a config value.

Disguise three: real threads can't talk to the hub

Now the readers are real threads. They find something interesting. They call socketio.emit() — and the server dies with greenlet.error: Cannot switch to a different thread.

Socket.IO's internals are green objects owned by the hub's thread. Touching them from a foreign OS thread is not allowed. So real threads never emit directly; they hand the event to a plain queue, and a greenthread drains it from the correct side (emit_bridge.py):

real OS thread  ──►  queue.Queue (real, not green)  ──►  emit_bridge_loop  ──►  socketio.emit
                     never blocks, sheds oldest         a greenthread,
                     when full                          drains every 50ms

The asymmetry is the whole trick: the producer must use a real queue because real threads use it, but the consumer must never block on get() — it uses get_nowait() and yields between passes. Block there and you are back to disguise one.

The same problem hit logging, which is not obvious until it happens: after monkey-patching, every log handler's lock is a green lock, so a real thread calling log.info() crashes the same way. Fixed by force-feeding logging real locks at startup (app.py:85-96), under a docstring that admits what it is: "This is a mitigation, not a cure."

The transferable lesson. Mixing an event loop with real threads means every boundary crossing needs an explicit, one-directional bridge. The three bugs above are one bug: a green thing and a real thing touched, and nobody wrote down which side owned it. If you've mixed a thread pool into an asyncio app, this is the same wound.

4 One radio, many consumers

Why the obvious answer — a mutex — is the wrong one.

Two browser tabs both hit POST /api/tune. Each handler kills the running rtl_fm and starts a new one. They interleave. Now there are two rtl_fm processes, one of them orphaned and holding the USB claim, and every tune from here until reboot fails with usb_claim_interface error -6.

The instinct is a mutex. It is wrong, and it is worth understanding why, because the reasoning generalises.

A mutex makes the second request wait for the first. But waiting is exactly what you don't want: switching takes one to two seconds, and by the time request A finishes, request B's frequency is the only one anyone cares about. You would spend two seconds tuning to a station nobody asked for any more, then two more seconds tuning away from it. Worse, under eventlet a blocked handler is a held connection.

You already know this

Debouncing a search box. You do not queue up a request per keystroke and serve them in order — you keep only the latest, because the intermediate states were never a goal, just typing.

→
Here it is in this repo

A slot of one plus a worker. New requests overwrite the pending one and count a superseded. Hardware only ever moves to the most recent intent.

# sdr_arbiter.py:112-128
def request(self, preset):
    if self._pending is not None:
        # Coalesce: the older commanded state is now irrelevant.
        self._superseded += 1
    self._pending = preset
    self._state = SWITCHING

So the route does not tune. It commands a tune and returns immediately — with 202 Accepted, not 200, because the honest answer is "queued", not "done":

return jsonify({"status": "commanded", "preset": preset, "sdr": snapshot}), 202

The UI then follows the hardware's real state over WebSocket rather than trusting its own optimistic update. Commanded state and actual state are separate fields in snapshot(), and the gap between them is visible in the console. This is the CQRS shape, arrived at by necessity: you cannot pretend a write is synchronous when it takes two seconds and can fail.

Who outranks whom

A lock says only "busy". Real contention here has priorities, because a satellite passing overhead is a deadline you cannot reschedule, and a background job collecting training data is not:

TierExampleRule
operatora person clicks a presetWins immediately. Always.
scheduledNOAA pass, WEFAX slotMay preempt decoders. Has a hard deadline — the satellite will not wait.
backgroundIQ corpus collectionNever takes the radio from a listener. Yields within ~1s.

"A person is using this" is not a state a lock can express, so it is modelled as a lease: any interaction stamps a timestamp, and background work refuses to start while the lease is live (OPERATOR_LEASE_S = 600). Ten minutes of "someone is here, leave the radio alone", refreshed on every click. It is a TTL cache holding a human's attention.

A bug this section found. When a satellite pass preempts the decoders, the code stops ISM, AIS, ACARS and Pager by iterating a tuple of receivers — and aprs_receiver is not in that tuple (app.py:398-407). An APRS session would hold the dongle straight through a scheduled pass. The same omission appears in the WEFAX path. Preemption written as a hand-maintained list will drift every time a decoder is added; it wants to be a registry.

5 Nine decoders, or: shelling out on purpose

The most boring architectural decision here, and the best one.

Decoding ADS-B or POCSAG from raw samples is genuinely hard signal processing, and it is solved. There are mature C programs for each, maintained by people who care deeply about that one protocol. So this app does not decode anything itself. It spawns them and reads their stdout.

You already know this

child_process.spawn() and newline-delimited JSON. Shelling out to ffmpeg instead of writing a transcoder, and parsing what it prints.

→
Here it is in this repo

subprocess_decoder.py, 241 lines, four hooks. Every decoder is 90–180 lines because the base class owns everything hard.

Subclasses implement four methods and nothing else:

HookReturns
build_cmd()the argv list, e.g. ["rtl_433", "-F", "json"]
build_source_cmd()optional upstream for a pipe: rtl_fm | multimon-ng
parse_line(line)one stdout line → a record dict, or None to skip
record_key(record)a stable identity, so repeat sightings update instead of duplicating

Everything else — process lifecycle, the real-thread reader, expiry, error attribution — is inherited. Three details in the base class earn their keep:

The record table is a TTL cache with merge semantics. Records key on the device, carry a seen timestamp, and expire after 600 seconds. Updates update() into the existing dict rather than replacing it, because a later sparse frame from the same sensor would otherwise erase fields the first frame carried. It is a cache with upsert, and the merge is the part that took a bug to learn.

Blame the right process. In a pipe, if the source cannot open the dongle, the downstream program sees EOF and exits cleanly with status 0 — so the naive symptom is "multimon-ng is broken" when the truth is "the radio was busy". The base class checks the source first and reads its stderr to produce an accurate message:

if "usb_claim_interface" in detail or "device busy" in detail.lower():
    reason = f"{src_cmd[0]} could not open the RTL-SDR — the device is "
             f"in use by another decoder or a leftover process"

The killall guard is narrow on purpose. Before starting, the decoder kills leftovers of its own binary. Both pipe-based decoders carry the same comment — PROC_NAME = "multimon-ng" # never rtl_fm — because rtl_fm is also the main audio pipeline, and a broad killall would take down the thing the user is listening to.

Not everything fits the base class, and that's fine. ADS-B and AIS don't parse stdout at all — dump1090 and rtl_ais expose TCP servers, so those two connect to a socket instead. Which incidentally means their readers can safely stay green: patched sockets yield, pipes don't. Same problem, opposite correct answer, and a comment in meteor_detector.py currently cites them as precedent for the wrong half of that.

The domain logic that is written here is the part no library could supply. The pager decoder has to tell real messages from noise, and the obvious test fails:

# pager_receiver.py:44-45
# Counting digits does not work here: the observed noise is ~75% digits
# and sails through any digit-fraction test.

The working test keys on characters that cannot legally appear in 4-bit BCD — [ and ] are unassigned codes in multimon-ng's table, so their presence marks the decode as low quality. You only find that by reading the decoder's source and staring at real garbage.

6 One transmission, end to end

Somebody keys a microphone eight miles away. Follow it through every file until it appears as text in a browser.

1  ·  A voltage in an antenna

hardware — RTL-SDR Blog V4

The dongle mixes the band down and samples it as pairs of numbers (in-phase and quadrature — "how far right" and "how far up" a spinning arrow points) 2.4 million times a second. That is all IQ ever means.

2,400,000 complex samples/sec

2  ·  A C program turns radio into audio

tuner.py:328-335 — builds the argv, spawns the child
cmd = ["rtl_fm", "-f", freq, "-M", mode, "-s", sr,
       "-r", "16k", "-l", str(self._squelch)] + gain + deemp + ppm + ["-"]

FM demodulation, resampled to 16 kHz because that is what Whisper wants, written to stdout as raw signed 16-bit PCM. The trailing - means "to stdout". Changing frequency means killing this process and spawning another one — there is no "set frequency" call.

16 kHz · mono · s16le on a pipe

3  ·  A real OS thread drains the pipe into two queues

tuner.py:403-420 — the thread from section 3
chunk = stdout.read(4096)                    # ~128 ms of audio
self.pcm_queue.put(chunk, timeout=0.5)       # → transcription (may wait)
self.audio_queue.put_nowait(chunk)           # → browser (drops if full)

Two queues, not one, so listening and transcribing never steal bytes from each other. This is the thread that must not be green.

4  ·  Branch A: straight to your speakers

audio_router.py:38-47 → GET /audio-stream

A generator yields a 44-byte WAV header and then never stops yielding chunks. The trick is in the header: both length fields are set to 0xFFFFFFFF, which is the conventional lie for "this file is infinite". The browser plays it as an ordinary <audio> element and never learns it's live. On an empty queue it emits silence rather than closing, because a closed stream is a reconnect and a reconnect is a gap.

5  ·  Branch B: where does one transmission end?

transcriber.py — VoiceActivitySegmenter

Whisper needs a clean utterance, not an endless stream. So: track a noise floor, and call it a transmission when audio rises above it and a split when it falls back for 300 ms. Minimum 1 second, hard cut at 15.

The floor is the 10th percentile of the last ~20 seconds — not the mean (speech drags it up) and not the median (on a busy channel the median is speech). Getting this wrong is not subtle:

A fixed threshold of 500 was in place first. Measured unsquelched FM hiss reads RMS 1342–1523 — roughly three times the gate. Every frame looked like speech. 280 chunks processed, 273 filtered: 97.5% waste, and the NPU spent its day transcribing static.
1–15 s of audio, silence-delimited

6  ·  Onto the NPU

transcriber.py:443-467 — backend selection

Audio becomes a mel spectrogram — a picture of which frequencies are loud over time — padded to exactly 10 seconds, then fed through two compiled Hailo binaries: an encoder and a decoder, greedily emitting at most 32 tokens. The backend is chosen at startup and degrades rather than fails:

Hailo NPU        →  a few ms     (needs a compiled .hef)
faster-whisper   →  CPU, slower  (automatic fallback)
none             →  drains the queue so it cannot back up

That last line matters: with no backend at all it still consumes the queue. A dead ML feature must not become a memory leak.

7  ·  Reject what the model made up

transcriber.py:231-245 — hallucination_reason

Whisper on near-silence confidently produces [Music], (roaring), or "Thank you." Five filters catch these: too short, known phrase, wholly bracketed, repetitive, short fragment.

Rejections are counted and the last one kept, deliberately — otherwise a working NPU that is correctly filtering junk is indistinguishable from a dead one, and you go debugging the wrong layer.

8  ·  One transcript, five consumers

app.py:364-378 — _on_transcript

The text now fans out: the browser feed, the keyword watchlist (which can raise a priority alert), the NOAA weather parser, the structured INTEL log line, and callsign correlation — extract anything shaped like a flight number and check it against aircraft currently overhead on ADS-B.

That correlator contains my favourite four lines in the repo, which are not clever engineering but hard-won observation:

# adsb_correlator.py — Common Whisper misheard variants
"a last car": "ASA",     # "Alaska"

9  ·  Out to every screen

app.py:1538-1553 — socketio.emit is replaced at startup

A wrapper sends each event to browsers and mirrors it over a Unix socket, so the physical LCD panel — a separate process, no eventlet, real threads — sees the same stream without knowing anything about HTTP. Monkey-patching your own emit function is a blunt instrument, but it guarantees no future call site can forget the fan-out.

socket.emit("transcript", {...}) → browser + LCD

Nine hops, four processes, two languages, one physical device. The interesting thing is how little of it is radio: stages 3 through 9 are queues, backpressure policy, fan-out and error handling — ordinary distributed-systems work that happens to have an antenna at one end.

7 Pushing to the browser

36 event types, and the pattern that keeps them testable.

REST here is for commands — 51 routes, mostly "do this", "give me that list". Everything continuous goes over Socket.IO, because polling a radio is absurd: the interesting thing happened 400 ms ago and won't repeat.

The pattern worth stealing is that no component imports socketio. Each one is constructed with an emit_fn and calls that:

self.emit_fn("transcript", segment)          # transcriber.py
self.emit_fn("apt_image_ready", {...})       # apt_decoder.py
self.emit_fn("emitter_identified", result)   # sei_model.py

Plain dependency injection, and it pays three times: unit tests pass a list's append and assert on what came out; the real-thread bridge is installed by injecting a different function; and the IPC fan-out was added by swapping the target once, centrally, with no component edited.

8 The frontend, which has no build step

Fourteen files, 5,300 lines, zero dependencies to install.

No React, no bundler, no node_modules. Each panel is an ES5 constructor function hung on window — prototype methods, an IIFE per file — instantiated when the socket connects, and the page is served by the same Flask app on the same port. D3, Leaflet and the Socket.IO client are vendored into static/vendor/ rather than pulled from a CDN.

Every panel has the same four-part shape, and it is worth copying: constructor takes the shared socket, sets up local state, subscribes to events, then does one REST fetch to backfill history. Socket.IO delivers the deltas; REST delivers the snapshot you missed before you connected. Neither alone is enough — a page opened five minutes in would otherwise show an empty table until the next event happened to arrive.

Worth noting what isn't here: the frontend never calls socket.emit() even once. Socket.IO is strictly one-way, server to browser. Everything the user does is an ordinary fetch() to one of the 51 REST routes. Commands go over HTTP where they get a status code and an error body; only the firehose goes over the socket.

That is not nostalgia, it is a deployment constraint: the node is meant to work air-gapped, in a field kit, with no uplink. A CDN link is a dead link the moment it matters, and a build step is a laptop you might not have. Editing ism.js over SSH and hitting refresh is the whole deploy story.

The one piece of build tooling that survived is cache-busting, because it fixed a real outage (app.py:717-735):

@flask_app.template_global("asset")
def _asset(filename):
    stamp = str(int(_os.path.getmtime(path)))   # mtime, not app version
    return f"/static/{filename}?v={stamp}"
Why mtime and not a version constant. Flask caches /static for twelve hours. A shipped JS fix would not reach an already-open console until a hard refresh — and a stale ravensdr.js here is not cosmetic: an old build force-tuned the radio on every page load. Any file edit now invalidates the browser copy automatically, with no version bump to remember.

9 The ML path, as plumbing

What /learn doesn't cover: not how the model works, but how it gets onto the chip and what happens when it isn't there.

Three models run on this node: Whisper for speech, a CNN for modulation type, and an RF fingerprinter. From a systems perspective they are all the same thing — a binary artifact, a fallback chain, and a threshold you will want to change at 2am without a redeploy.

The artifact cannot be built here

The Hailo-8L is inference-only, and its compiler is x86-only and behind a login. So the lifecycle straddles two machines, which is the single most important fact about doing ML on this box:

on a laptop/VM (x86)                        on the Pi
─────────────────────                       ─────────
PyTorch training
   ↓ torch.onnx.export
model.onnx  ──────────────────────────────►  onnxruntime on CPU   (works today)
   ↓ Hailo Dataflow Compiler
   ↓   └─ quantize to INT8 using a
   ↓      CALIBRATION SET  ◄──────────────── sampled from THIS node's spectrum
model.hef   ──────────────────────────────►  Hailo NPU            (a few ms)

Note the arrow pointing left, because it is the part people miss. INT8 quantisation picks its scaling factors by running a hundred or so representative samples through the graph. Show it generic data and the scales are wrong for your signals — and wrong in the worst way, invisibly: the graph compiles, the model runs, the accuracy is just quietly worse. So the calibration set is replayed from this node's own captures, through the exact preprocessing the runtime uses (ml/signal_classifier/export_calibration.py):

Matches signal_classifier._infer_hailo():
    224x224 grayscale spectrogram -> stacked to 3 identical channels -> NHWC.

That "matches" comment is doing real work. If the calibration preprocessing and the runtime preprocessing drift apart by so much as a channel order, you have quantised the model for data it will never see.

The corpus this all runs on is the interesting bit. 253,000 IQ captures, 71 GB, written by the node itself while it was doing its normal job — each labelled with the tuned preset's declared modulation rather than the classifier's own guess, so the labels stay independent of the thing being trained. It is also lopsided in a way worth staring at: 68,000 samples of WFM and two of AM. A quarantine directory holds another 2,000 with names that read like a lab notebook — OOK-FSK-ambiguous, OOK-empty-345, mislabelled-adsb.

Fallbacks are the feature

Every model has a degradation ladder, and the app is expected to keep running at every rung:

RungSpeechModulation

floorpassthrough — drain the queue, transcribe nothingheuristics: can only ever say WFM/FM/CW/AM/SSB

A mid-session Hailo failure drops to CPU and re-enters the loop rather than taking the process down. You can also pin a backend with RAVENSDR_FORCE_BACKEND, which fails loudly if the pinned one is unavailable — a deliberate asymmetry: automatic selection should degrade quietly, explicit selection should never silently do something else.

The trap that fails silently. torch.onnx.export writes tensors as NCHW; HailoRT expects NHWC. Same model, same weights, different memory layout. Feed the wrong one and you get no error at all — just confident nonsense. Each backend builds its own tensor for this reason. If you have ever chased a channels-first/channels-last bug, you know it costs a day.

One chip, three models — the antenna problem again

Section 4 was about one radio and nine decoders. The NPU has the identical shape: one physical chip, three models that all want it. Constructing a Hailo VDevice the obvious way — each model making its own — means whichever model initialises first takes the chip and the others get nothing.

So there is one shared device handle with round-robin scheduling (hailo_device.py), acquired by all three consumers. Same lesson as the dongle, learned twice on different hardware: a scarce physical resource needs exactly one owner in the program, and everyone else asks that owner. The version of this bug you have already met is two ORM instances each opening their own connection pool.

Thresholds live in config, not in constants

Every decision boundary that used to be a module constant is now a key in config.json with an apply_settings() on the owning module, editable from the Settings tab: match threshold, segmenter dB, silence threshold, VAD dB, classifier confidence. Changing one takes effect without a restart — which matters because the correct value is discovered by watching live signals, and a restart costs you the transmission you were studying.

10 Testing hardware you don't have

33 test files. None of them need a radio, and that is the point.

If the tests required an antenna they would run once, on one machine, in one city, in good weather. So the seam is drawn at the process boundary: everything above subprocess.Popen is testable, and what's below it is somebody else's C program.

Three things make that work, and all three are decisions made for testability that turned out to be good design anyway:

  • Parsers are pure functions. parse_line() takes a string and returns a dict. A captured line of real rtl_433 output is a complete test fixture — no process, no device, no timing.
  • Emit is injected. Pass a list's append as emit_fn and assert on what the component tried to send.
  • Audio is just bytes. Synthesise a sine wave in numpy and feed it to the segmenter; it cannot tell the difference between that and an antenna.

What this deliberately does not test is whether rtl_433 is installed, whether the dongle enumerated, or whether the antenna is pointed at the sky. Those are real failure modes and they are checked at runtime with explicit error messages instead — which is why so much of section 5 is about attributing failures to the right process. The tests cover logic; the error messages cover hardware.

Two details are load-bearing rather than incidental:

KillMode=control-group. When the service stops, systemd kills the entire cgroup, not just the Python process. Without it, an orphaned rtl_fm or ffmpeg survives the restart, keeps the USB claim, and the freshly started service cannot open its own radio. The unit file is doing hardware cleanup that the application cannot guarantee, because the application might be the thing that crashed.

Config writes are atomic. Write to a temp file in the same directory, then os.replace(). A half-written config.json from an unlucky power cut would mean a node that will not boot — and this machine is expected to lose power without warning. There is no fsync before the rename, so it is durable against a crashed process but not against a power loss at the wrong microsecond; an honest description of the guarantee is worth more than assuming the strong one.

And one thing that is simply wrong. ravensdr.service — the unit that actually runs this node — exists only in /etc/systemd/system/. It is not in the repository. Every other unit file is version-controlled. Rebuild this Pi from a clean SD card and you get all the code and none of the thing that starts it. This is the highest-value five-minute fix on the page.

12 Rough edges, honestly

A tour that only shows the good parts teaches nothing. These are live, in the code, today.
bug

Two browser tabs cut each other's audio in half

Every listener consumes from the same audio_queue. There is no subscriber list, so two tabs are competing consumers and each gets roughly every other chunk. Both hear choppy audio and neither is obviously at fault. Needs a real fan-out: one queue per client, registered on connect.

bug

APRS is not preempted by a satellite pass

The preemption loop lists ISM, AIS, ACARS and Pager by hand; aprs_receiver was added later and never joined the tuple, in either the APT or the WEFAX path. Any hand-maintained list of "all the decoders" will drift — this wants a registry the decoders enroll themselves in.

not real yet

RF fingerprinting is running on random numbers

The SEI model — identify a specific transmitter by its hardware imperfections — has a full pipeline: collection keyed on ADS-B aircraft IDs for ground truth, a 1D CNN with attention, triplet-loss training, ONNX export, a Hailo compile step. None of it has ever been run. There is no .hef, the data and checkpoint directories are empty, and the CPU fallback path is explicit about what it does instead: "no HEF model, using CPU fallback (random embeddings)". The emitter table in the UI is populated by cosine similarity over noise. Scaffolding is not a feature, and a fallback that silently produces plausible-looking output is worse than one that refuses.

half-done

The UI/radio split is real code that isn't deployed

The plan was to separate the process that owns the hardware from the process that serves the web console, so a UI crash can't take the radio down and the radio half can drop eventlet entirely. The IPC layer, the client, the second Flask app and a third peer driving the LCD all exist and work. But app.py is still both halves at once, still monkey-patched, still serving all 51 routes — and ravensdr-ui.service is in the repo but not installed. What runs today is the monolith plus the LCD driver.

latent

A function that would crash if anyone called it

get_presets_by_category() builds its dict from CATEGORIES (8 entries) but presets reference CATEGORY_LABELS (9 — it has packet, the list doesn't). The APRS preset is category packet, so the function raises KeyError. It is never called; the UI groups client-side. Dead code with a live bug in it, which is the worst kind: it looks tested because nothing complains.

inconsistency

One bug fixed, its twin left alone

Exiting APT mode used to blind-sleep for the length of the satellite pass — so if the capture died immediately, the radio stayed locked for fifteen minutes doing nothing. That was fixed by polling whether recording is genuinely in progress. The identical code in the WEFAX exit path still blind-sleeps. Finding a bug class and fixing one instance is how you get two behaviours from one design.

smell

Config is re-read from disk on every transcript

The keyword scanner calls get_settings() per transcript, and that calls load_config(), which reads and parses the JSON file. It is fast enough not to notice and wrong enough to fix — the file is the source of truth, but it does not need to be consulted on the hot path.

fixed

The one that started all this

A blocking pipe read in a green thread froze the entire web console while the radio kept working perfectly. Diagnosing it meant realising that 1.2% CPU is the signature of a deadlock, not a busy loop — a spin would have pinned a core. Everything in section 3 is the scar tissue from that afternoon.

13 What the NPU could do next

Where new model work would plug into everything above.

The chip is a 13-TOPS INT8 vision engine. The most productive way to think about it is: anything you can turn into a picture, it can classify cheaply — and radio turns into pictures very naturally, which is what a spectrogram is.

IdeaWhy it fits this chipWhere it plugs in
Spectrogram signal classifier Literally image classification — the canonical shape for this hardware. Small enough to train and recompile in an afternoon. iq_segmenter → signal_classifier
APT image enhancement Denoise/super-resolution CNNs quantise well to INT8, and the before/after is visible to the naked eye. apt_decoder output
Whisper pre-filter A tiny always-on VAD/keyword model gating an expensive one. Cuts NPU load rather than adding to it. transcriber, ahead of Whisper
RF anomaly detector Autoencoder on "normal" spectrum; high reconstruction error means something new is transmitting. Unsupervised, so no labelling. iq_segmenter → priority_alert

All four need the same missing piece, which is why it is worth building once: a model registry with hot-load. Today each model's path is effectively fixed at startup. What the roadmap wants is the ability to drop a new .hef onto the node, point a config key at it, and have the owning module swap it without a restart — the same shape as apply_settings() in section 9, one level up. Combine that with exporting a calibration set from the node's own captures and you have a genuine train → quantise → deploy loop that runs on a laptop and a Raspberry Pi.

What "training on the NPU" actually means. Nothing trains on this chip — it runs fixed weights and that is all it does. The loops genuinely available on-device are: collect and label data, curate the fingerprint database, and tune thresholds against live signals. The weight-changing loop happens elsewhere and comes back as a file. Being precise about which loop you are in saves a lot of wasted effort.
